# 模块检测下一阶段执行计划

基线：ca80925 的入口保护实现，加本轮 BoundaryLens 更名及内部接入基础。
第 0 步已通过本地契约验收，其余步骤按下列范围继续；产品仍限定 Dart 包内的文件级边界。

后续范围修订：首版不提供用户自定义规则，先完成以下内部基础与原模块使用闭环。
见 [ADR-0003](adr/0003-built-in-first-extensible-core.md)。每一步分别记录证据，
不因已有接口或测试数量而宣称其余标准已经满足。

## 0. 内置规则接入基础（首版前置）

状态：本地实现验收通过。RuleRunner 与 rule_contract_test 覆盖唯一注册、输入准备、
范围、类型预校验、禁用、事实不足、诊断隔离与输出归属；IDE 协议保留执行覆盖。
配置无效时 config check 保持 exit 1、scan 保持 exit 2。

目标：使用现有事实能力增加内置规则时，不必修改 scanner 主循环和 IDEA 展示逻辑。

- 单一注册入口：元数据、默认值、输入需求和执行归属一致；启动/测试验证 ID 唯一，
  不引入用户命名空间、分发版本系统或第二套目录。
- 输入与范围：明确需要目标文件、项目上下文或共享引用图，以及 changed-only 是否支持；
  不依靠规则 ID 名称分支偷偷构建图，不承诺未实现的类型/数据流能力。
- 参数与执行：默认值和允许类型分开定义；统一校验参数、跳过禁用规则，
  现有 detector 仍保留必要防御，不将“配置加载成功”等同于运行完成。
- 结果与证据：已启用的架构检查区分未执行、完成、不完整及原因，
  诊断保留来源；不改写 severity/domain，不把诊断伪造成代码 finding。
- 输出边界：CLI 产生同一份结果供 IDE/CI 消费；保留 JSON/SARIF、单文件、
  抑制与 baseline 契约。已有 coverage.moduleBoundary 保持兼容。

验收：通过一条仅使用已有事实的内部测试规则验证接入、禁用、无效参数、
事实不足与 findings 输出；不为测试规则增加正式产品规则或维护第二份注册表。
对现有模块规则回归验证同一协议和范围。没有实际消费者的抽象不作为首版交付。
本阶段不实现自定义 YAML 规则语法、脚本执行、外部依赖加载或通用能力编排平台。

## 1. 配置可定位、归属可解释（先执行）

目标：用户能够从错误回到具体模块声明，避免拼错键后只得到笼统 partial。

- 改动入口：config_loader.dart、config_tools.dart、source_workspace.dart、边界专属测试。
- 为架构字段的无效类型/未知键、重复模块、重叠归属、失效入口保留配置路径与 YAML 位置。
- scan/config check 共用一条验证链；无效声明仍 exit 2，不能变成代码 finding 或低严重度警告。
- 明确区分省略 entry_points（旧模式，partial）和 []（不开放入口，完整配置）；
  后者的修复建议应说明“模块没有公开入口”，而不是显示空路径。
- 诊断保留文件/行/原因；一个归属冲突列出冲突双方，不靠配置顺序选择。

验收：同一错误从 scan 和 config check 得到一致原因；拼错 entry_points、重叠、
空列表、入口越界/被排除/不存在分别有正反例；配置错误不产生虚构 module_violation。
先聚焦测试，再完整 Dart 门禁；此步不增加新规则 ID。

## 2. 增量扫描明确提示失效范围

目标：配置或入口变化时，未改动的调用者不能被漏掉后仍呈现“模块整体已通过”。

- 改动入口：file_collector.dart、scan_context.dart、scanner.dart、报告与 Git 临时项目测试。
- 保留 Git 变更事实，包括删除，识别实际选用配置、pubspec 身份及声明入口的变动。
- 第一版先在 coverage 中提示需要包扫描及具体原因，不悄悄扩大 --changed-only 的
  findings 范围；单文件请求继续是单文件。IDE 可以显式提供包扫描入口。
- 非 Git、无效 base、仅配置变化、入口删除/改名、条件 export 变化要有独立用例；
  不能把 Git 不可用后的全量退化继续标成 changed。
- 若以后需要反向依赖增量，先以全包扫描结果为 oracle 验证，再讨论优化；本阶段不建缓存平台。

验收：只有配置发生变化且 Dart 调用者未改动时，报告仍明确提示全包重查；
调用者修改继续保持原 changed-only 定位。JSON/SARIF 与 IDE 显示同一范围和原因。
任何 coverage 外部字段扩展先更新外部规范并保持旧消费者可解析。

## 3. IDE 从纯文本报告走到证据导航

目标：点到来源与目标，比增加全景图或评分更直接地帮助修复。

- 改动入口：BoundaryLensProtocol、ScanAction、Configurable 与独立 UI/协议测试。
- 保留 CLI 的诊断路径、位置、coverage reasons；不压成丢失来源的字符串。
- 以简单列表展示：来源引用、目标文件、来源/目标模块、触犯的声明、允许入口。
  支持打开来源、目标或配置位置；无可靠位置的诊断保留为项目级项。
- 未配置显示创建配置的操作指引；检查不完整显示原因；complete 仍只表示本次范围可检查。
- 不自动放宽 allowed_deps、不自动把私有文件加入入口、不猜测“正确架构”。

验收：新示例的坏引用可导航，修复后重扫消失；零 findings、partial、失败、取消、
嵌套包与未信任项目均有明确反馈。插件 check/native smoke 之后必须做新 UI 人工实测。

## 4. 获授权的真实项目试点

由用户指定一个项目及两个模块；先读取已有公开 API 与边界约定，再生成最小配置。
不自动绑定 Forge 或消费者注册表，也不扫描所有项目。

记录实际配置与维护时间、误报、漏报、能否给出可操作修复；至少验证：
合法入口、绕过入口、同模块内部引用、合法 facade export、条件引用、归属不明。
以具体案例决定是否删除或改进规则，不生成“架构健康总分”。

## 执行顺序与提交边界

更名验证 → 内置接入基础 → 配置诊断 → 增量失效提示 → IDE 导航 → 两模块试点。
每一步独立提交和验收，失败留在当前步骤，不把后续能力写成已经支持。
CLI 仍拥有规则和范围事实，IDE 仍是适配器。首版不引入逐类职责 DSL、通用状态机、
跨语言解析器、完整数据流或运行时 SDK。名称/版本/平台/市场发布门禁与本计划独立。
